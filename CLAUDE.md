# CLAUDE.md

## Project Overview

**Kidock** — the dock where your agents' work arrives.

A **read-only desktop viewer** for Markdown deliverables that AI agents (Claude Code, etc.) write into local folders. The name comes from 既読 (*kidoku*, "already read") + *dock*. Built for personal use at work and at home, but aimed at OSS-publishable quality.

### Functional Requirements

- Register multiple folders in the left sidebar and show a tree for each.
- Watch each registered folder recursively. New or updated `.md` files get an **unread mark** and trigger an **OS notification**.
  - Unread counts are aggregated per folder and shown as badges.
  - Opening a file marks it read. "Mark all as read" is supported.
  - Read/unread state persists across app restarts.
- Render Markdown (GFM) with syntax-highlighted code blocks.
- Render **Mermaid** diagrams.
- Support **images embedded via relative paths**, resolved against the `.md` file's directory. Relative links between `.md` files open inside the app.
- Re-render automatically when the displayed file changes, preserving scroll position as much as possible.
- Target OS: Windows and macOS (Linux: best effort).

### Out of Scope

- Editing. Kidock never modifies the files it displays.

### Design Constraints

These apply to every Issue. Revisit them when designing anything that touches file watching, rendering, or persistence.

1. **Atomic writes**: agents often save by writing a temp file and renaming it over the target. Judging changes by path or event kind alone causes missed or duplicate detections. Debounce events, and decide "actually changed" by path + mtime/size (plus a content hash when needed).
2. **Security**: treat displayed Markdown as **untrusted input** generated by an agent. Sanitize HTML, never execute scripts, set a strict CSP, and serve local files (images) only from inside the registered folders.
3. **Noise exclusion**: exclude `.git`, `node_modules`, hidden files, and temp files from watching. Exclusion patterns must be configurable.
4. **Large folders**: the sidebar must stay responsive with thousands of files (lazy loading / virtualization; don't push the whole tree over IPC at once).
5. **Path differences**: account for separator and case-sensitivity differences between Windows and macOS. Normalize paths at a single boundary.

## Tech Stacks

- State persistence: SQLite via `rusqlite` (bundled), owned by the Rust backend (introduced in #3).

- Clipboard: `tauri-plugin-clipboard-manager` 2.x, used only from Rust (introduced in #21).

## Implementation

You must follow TDD (Test-Driven Development) principles when implementing the tasks.
This means you must write todos to complete the task first, then write a test that fails, and finally implement the code to make the test pass. Then refactor the code if necessary.

### Layering

- **Rust backend** (`src-tauri/src/`): `domain` / `infra` / `commands` (+ `state.rs`).
  - `domain`: pure logic (change detection, unread state, exclusion rules, path normalization). No Tauri, no filesystem I/O.
  - `infra`: adapters for the filesystem, `notify`, persistence, and OS notifications.
  - `commands`: thin Tauri command / event handlers that wire `infra` to `domain`. Each `#[tauri::command]` delegates to a plain `do_*` function taking `&AppState`, so it is testable without a Tauri runtime.
  - Keep dependencies pointing inward: `commands` and `infra` may depend on `domain`, but `domain` must not depend on the outer layers.
- **Frontend** (`src/`): all backend access goes through the `KidockApi` interface (`src/api/`), provided via React context (`ApiProvider` / `useApi`). `tauriApi` is the real implementation; `mockApi` is used in tests and in browser dev. Components never import `@tauri-apps/api` directly.
- **Path rule**: the frontend sends an absolute path only when registering a project (`add_project`, from the folder dialog). Every other request uses `(projectId, rel)`, where `rel` is a `/`-separated path relative to the project folder, validated by `RelPath` and checked again after canonicalization.
- **Change detection** (#6): `infra::watcher` (one `notify-debouncer-full` watcher per project) only *nominates* paths. `infra::detector` (a single worker thread) re-checks each one with `infra::scan` and decides with `domain::change::decide` from the stored `(size, mtime, hash)`. Event kinds are never trusted. Detected changes go to a `ChangeSink`: `AppSink` records them in the Inbox (`inbox_items`, rules in `domain::inbox`) and *then* emits `kidock://changes`, so the UI's refetch sees the new items. It also forwards each batch to `infra::notifier`, which coalesces a 2 s burst into one OS notification (`domain::notice`). Notifications are skipped while the main window is focused or when the toggle is off. A click emits `kidock://open`. New projects get a silent `Baseline`; at startup, baselined projects get a `Rescan`, which reports changes made while Kidock was closed.
- **Exclusions** (#12): glob patterns per path component (`domain::filter`, defaults in `DEFAULT_PATTERNS`), edited in the UI and stored in `settings` (`exclusions.patterns`). `AppState::rules()` returns a snapshot, so take one per operation and never hold the lock during I/O. Changing the patterns silently re-baselines every project.
- **Persistence**: SQLite (`rusqlite`, bundled) at `<app data dir>/kidock.db`, e.g. `~/Library/Application Support/io.github.satoryu.kidock/` on macOS and `%APPDATA%\io.github.satoryu.kidock\` on Windows. `infra::store` owns the schema. Add a new entry to `MIGRATIONS` for every schema change; never edit a released migration. `AppState` caches projects; writers take the `projects` lock before the store lock.

## Testing

- **Rust**: `cargo test`, `cargo clippy` (warnings as errors), `cargo fmt --check`.
- **Frontend**: [Vitest](https://vitest.dev/) + [Testing Library](https://testing-library.com/), plus the TypeScript type-check.

```bash
# Rust (run from the repo root)
cargo test --manifest-path src-tauri/Cargo.toml
cargo clippy --manifest-path src-tauri/Cargo.toml --all-targets -- -D warnings
cargo fmt --manifest-path src-tauri/Cargo.toml --check

# Frontend
npm test            # run the whole suite once
npm run test:watch  # watch mode
npm run typecheck   # tsc --noEmit (also runs as part of `npm run build`)
npx vitest run --project scripts   # repository tooling only (hooks, CI helpers)
```

IPC-level frontend tests use `mockIPC` from `@tauri-apps/api/mocks`. `clearMocks()` runs after each test via `src/test/setup.ts`. On the Rust side, `src-tauri/tests/ipc.rs` invokes commands through Tauri's mock runtime with the same JSON bodies the frontend sends (camelCase argument names). `src-tauri/tests/watch.rs` drives the real watcher (FSEvents / ReadDirectoryChangesW) on temp dirs and runs on both CI OSes. Add a case there for any change to watching or detection. `ipc.rs` also has an `#[ignore]`d test that writes to the real clipboard (`cargo test --test ipc -- --ignored`). Extend `ipc.rs` whenever a command's signature changes, so `tauriApi.ts` and the Rust commands cannot drift apart. It is skipped on Windows (`#![cfg(not(windows))]`): test executables there lack the Common Controls manifest that the Tauri runtime needs (`STATUS_ENTRYPOINT_NOT_FOUND`).

Vitest has two projects (`vite.config.ts`): `web` (jsdom, `src/**/*.test.{ts,tsx}`) and `scripts` (Node, `scripts/**/*.test.mjs` and `.claude/**/*.test.mjs`). Repository tooling is written as Node ESM scripts so it runs on Windows without Git Bash; keep the logic in pure functions under `scripts/lib/` and test those.

## Manual Verification (Desktop App)

When the Test Plan includes manual verification items, you must perform the verification yourself as far as the environment allows. Only hand an item to the user when it genuinely cannot be done here, and then give them exact steps and the expected result.

1. **Frontend in a browser (fast loop)**: `npm run dev:mock` serves the UI at `http://localhost:1420` with the in-memory mock API (`.env.mock` sets `VITE_API_MOCK=true`; sample content lives in `src/api/sampleFiles.ts`, including an XSS sample and a 1,000-file directory). Verify layout, tree behavior, unread badges, and rendering (GFM, code highlighting, Mermaid, relative images/links) with the Chrome integration tools. This does not exercise Rust, the real filesystem, or OS integration.
2. **Real app**: `npm run tauri dev` and verify end to end. On macOS, use computer-use to drive the native window when needed.
3. **File-watching scenario** — use a disposable verification folder (e.g. under the scratchpad), register it in the app, then:
   1. Create a new `.md` → unread mark + folder badge increments + one OS notification.
   2. Overwrite an existing `.md` in place → marked unread again; if it is open, it re-renders and keeps scroll position.
   3. Atomic save: write to a temp file, then `mv` it over the target → detected exactly **once** (no miss, no duplicate notification).
   4. Rename a `.md` → tree updates; unread state follows the documented rule.
   5. Touch without content change (same content rewritten) → follows the documented rule (no false "updated" if the design says so).
   6. Create files under `.git/`, `node_modules/`, hidden paths, and temp-file patterns → ignored.
   7. Open a file → read; "mark all as read" → badge clears; restart the app → state preserved.
4. **Items that differ between Windows and macOS** — call these out explicitly in the Test Plan and verify on each OS (Windows is usually verified by the user or CI):
   - File-watcher event sequences for atomic saves/renames (FSEvents vs. ReadDirectoryChangesW).
   - Path separators, drive letters, case-insensitive matching, and paths containing spaces / non-ASCII characters.
   - OS notification permission prompts and appearance.
   - WebView differences (WKWebView vs. WebView2) in rendering, fonts, and custom-scheme URL formats (`kidock-asset://localhost/…` vs. `http://kidock-asset.localhost/…`).
5. Check off the verified items in the PR Test Plan, noting which OS each item was verified on.

## Merging

Do not merge a PR if there are unchecked items in its Test Plan. For items that cannot be verified by automated tests (e.g. manual verification), perform the verification yourself first. Only ask the user for approval if the environment is genuinely unavailable.

## Definition of Done

Merging is not the end of the work. An Issue/PR is done only when all of the following hold:

1. CI (`.github/workflows/ci.yml`) is green on **both Windows and macOS**, and the merge is chained to it. Never merge as a separate step that ignores the CI result:

   ```bash
   HEAD_SHA=$(git rev-parse HEAD)   # the pushed commit you verified
   node scripts/watch-pr.mjs <PR> --head "$HEAD_SHA" &&
     gh pr merge <PR> --squash --delete-branch --match-head-commit "$HEAD_SHA"
   ```

   `watch-pr.mjs` exits 0 only when every check passed and both `check (macos-latest)` and `check (windows-latest)` ran, for the commit given by `--head`. It exits non-zero on failure, cancellation, missing jobs, no checks, or a PR head that never reaches (or moves away from) that commit. `--match-head-commit` makes the merge itself refuse any other commit, so a push between the watch and the merge cannot slip in unverified. If the workflow's job names change, update `REQUIRED_CHECKS` in `scripts/lib/checks.mjs` (or pass `--require <name>`).
2. After merging, watch the CI run on `main` until it completes green:

   ```bash
   git fetch origin main
   gh run watch "$(gh run list --branch main --commit "$(git rev-parse origin/main)" --workflow CI --limit 1 --json databaseId -q '.[0].databaseId')" --exit-status
   ```

3. Record the verification results on the PR / Issue before closing it.

## Verification Principles

- **Never implement from memory**: verify APIs, commands, config keys, and permissions of external tools and libraries (Tauri v2 capabilities/plugins, `notify`, markdown-it, mermaid, shiki, etc.) against official docs before implementing. Tauri v1 and v2 differ significantly; do not reuse v1 knowledge.
- **Grep the blast radius before changing code**: find callers, tests, and fake/mock implementations first, then design the change. When the plan is to replace only *part* of an implementation of a multi-method interface (e.g. swap one method's data source but keep another), grep the callers of **every** method on that interface, not just the one you're changing — a design that looks like a clean partial swap can silently break an unrelated method's callers.
- **Separate backend state from frontend state**: when debugging, observe the Rust side (logs, emitted events, persisted state) and the WebView side (DevTools console, rendered DOM) independently before hypothesizing a cause.
- **Test with real filesystem behavior**: unit tests with synthetic events are necessary but not sufficient for file watching. Verify against real atomic saves on the real OS before declaring watcher changes done.

## Known Pitfalls (project-specific)

- **Atomic saves look like create/remove/rename sequences**, and the exact sequence differs per OS and per editor/agent. Never infer "updated" from a single event kind; debounce, then compare path + mtime/size (and hash if needed) against the last known state.
- **The watcher can fire for the temp file before the rename**: temp files must be filtered by the exclusion rules, not shown in the tree or counted as unread.
- **Markdown is untrusted**: raw HTML, `javascript:` URLs, SVG with scripts, and Mermaid labels are all attack surfaces. Sanitize after rendering, and keep the CSP strict. Project images are served by Kidock's `kidock-asset` scheme (`infra::asset_protocol`), which checks the project id, `RelPath`, canonical containment, and an image-type allowlist. Tauri's built-in asset protocol is disabled: its scope matches path strings, so a symlink inside a project could expose files outside it. Links leave the app only through the `open_external` command (http/https/mailto); the WebView has no opener permission. Likewise, the clipboard is reachable only through the write-only `copy_text` command (`infra::clipboard`, #21); the WebView has no `clipboard-manager:*` permission, so a page can never read the clipboard.
- **`freezePrototype` is off** (owner decision in #10): Mermaid's dayjs assigns to built-in prototypes at load time, which throws once they are frozen. Because the prototypes are not frozen, every Mermaid source goes through `stripConfig` (no `%%{init}%%` or front-matter config). Mermaid runs in `strict` mode with `htmlLabels: false`, and its SVG is sanitized again. Keep all of that, and never merge untrusted objects into config or state with a deep-merge helper.
- **The CSP is not applied in desktop `tauri dev`**: the WebView loads the Vite dev server URL directly (Tauri 2.12 proxies dev requests, and thus applies the CSP, only on mobile). Verify CSP-sensitive changes with a built app (`npm run tauri build -- --debug`), or by serving a build with the same CSP header. Chrome reports `script-src-attr` violations when *parsing* HTML that contains inline handlers (e.g. DOMPurify's `DOMParser` step) even though nothing executes; check the final DOM rather than treating such a report as a sanitizer failure.
- **Relative paths resolve against the `.md` file's directory**, not the registered folder root or the app's CWD. Reject resolved paths that escape the registered folders.
- **Path comparison**: normalize separators and casing rules in one place; never compare raw path strings across the IPC boundary. Windows paths may also come with the `\\?\` prefix after canonicalization.
- **Large trees**: do not send the full recursive tree over IPC in one payload; load children lazily.
- **Sync Tauri commands run on the main thread**: a plain `#[tauri::command] fn` blocks the UI while it does I/O. Declare I/O commands as `#[tauri::command(async)]` (runs a sync fn on the thread pool) or as `async fn` (verified in tauri-macros 2.7 `command/wrapper.rs`).
- **Do not use `git add -A`** (or `git add --all` / `git add .`): always stage explicit paths. Enforced by the PreToolUse hook in `.claude/settings.json` (`.claude/hooks/guard-git-add.mjs` → `scripts/lib/gitAddGuard.mjs`), which also blocks `-u`, `./`, `:/`, and `*`. It is a guardrail, not a sandbox: it does not see through `eval`, aliases, or `sh -c`, so don't try to work around it. If it blocks a legitimate command (a false positive), fix the guard with a test instead of rephrasing the command to slip past it.
